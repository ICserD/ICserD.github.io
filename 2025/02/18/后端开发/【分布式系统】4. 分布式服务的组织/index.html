【分布式系统】4. 分布式服务的组织

发表于2025-02-18|更新于2025-02-19|后端开发系统设计
|字数总计:4.7k|阅读时长:16分钟|阅读量:

分布式服务是由各个独立部署的不同服务组织而形成的系统，对外提供一个系统性的功能。比如一个电商系统，分为订单服务、账户服务、库存服务等等。

本文，我们主要关注当系统由多个独立部署的服务组成时，我们如何组织协调这些服务，使得整个系统协同高效运转。

一、分布式服务的组织

（一）从一个电商系统说起

假设我们设计一个简单的电商系统，核心功能包括：下单、扣库存、扣余额。在单体架构中，可能会分为几个模块：订单模块、账户模块、库存模块。他们运行在同一个进程中，通过本地方法调用进行协作。

随着业务增长、访问量变大、团队规模扩大后，单体架构面临不可调和的矛盾：

  • 难以扩展
  • 部署耦合严重，团队开发效率低
  • 一个模块出问题影响整个系统

于是系统开始往分布式服务发展，进行系统拆分，将原来单体系统拆分成独立的几个子服务：

  • 订单服务
  • 账户服务
  • 库存服务

每个服务独立部署、独立扩容，通过网络进行通信，这是分布式系统的雏形。

（二）分布式服务的整体架构

1. 服务拆分后面临的五大问题

当系统拆分为多个服务后，新的问题接踵而至，分类来看，主要存在 5 大问题：

  • 外部流量如何接入：从前用户请求到来直接负载均衡后请求一个服务实例就行，现在面临多种类型的服务实例，在入口层维护各个服务的域名显然不是一个明智的办法
  • 内部服务如何通信：从前各个模块都在单体实例上，在同一个进程内，直接通过方法调用即可；现在服务拆分后，各个服务独立部署，处于不同进程、不同实例，因此只能通过网络调用的方式进行通信
  • 服务实例如何发现：在分布式环境中，各个服务随时可能水平扩展（扩容、增加机器节点等），容器的 IP 是动态的、实例也可能宕机，如果每个服务都通过配置维护其他服务的地址，不仅繁琐而且无法适应动态变化
  • 配置如何统一管理：每个服务不仅独立部署，而且都拥有自己独立的配置，如果分散在不同服务的配置每次修改都要重新打包部署，将严重影响运维效率
  • 出问题如何进行排查：不同单体服务，通过进程的方法调用栈就能追踪到问题，但是对于分布式服务，调用链涉及到多个服务，错综复杂，难以排查问题

2. 经典的分布式服务架构

为了解决上述五大问题，各种分布式组件诞生，逐渐构筑出分布式系统的经典组织架构。

“在计算机的世界里，没有事抽象一层解决不了的，如果有，那就再抽象一层。”

2.1 API 网关

不同于计算机网络中网络层的网关，这里指的是分布式服务体系下的网关。为了解耦“外部流量管理”与“内部业务逻辑”，在客户端和分布式服务之间抽象出一层网关，统一管理外部请求，提供鉴权、限流、熔断、路由、监控等功能。

在分布式服务中引入网关，可以带来如下的收益：

  • API 网关服务对外提供统一的入口供客户端访问，隐藏系统架构实现的细节，让分布式服务的使用更加友好
  • 借助 API 服务网关可以统一做切面任务，避免每一个服务单独开发，提高开发效率，使得系统更加标准化
  • 通过 API 服务网关统一做鉴权，可以更高效地实现鉴权，提高系统安全性

同时，引入网关也伴随着增加系统复杂性的问题：

  • 新增了一个需要运维的系统
  • 在服务发布和部署阶段需要管理网关的配置，保证外部 API 访问的是正常的服务
  • API 网关服务本身需要是一个高可用的伸缩性强的系统，避免单点故障，否则会成为整个分布式系统的瓶颈

2.2 服务通信（RPC）

2.2.1 RPC 概述

原本单体的各个模块被拆分成独立部署的服务，原本的本地方法调用也要转变成通过网络进行交互，于是 RPC 调用方式诞生了。

RPC，Remote Process Call，远程过程调用，顾名思义，是一种旨在使得服务之间的调用像调用本地方法一样，对开发者屏蔽底层网络细节，使得开发者更加关注业务逻辑的实现的一种调用模型。

2.2.2 RPC 原理

RPC 本质上做了五件事：

  • 代理拦截本地方法调用
  • 将调用信息序列化为网络请求
  • 通过服务发现和负载均衡选择远程服务，将网络请求发送出去
  • 在远程执行真实方法
  • 将调用结果反序列化后返回

而这五件事都通过在本地实现/生成的远程代理完成。

以下单扣库存为例子，介绍 RPC 的工作过程：

  1. 订单服务处理下单逻辑，然后调用**库存服务代理（Proxy）**的 deduct 方法
  2. 库存服务代理拦截方法调用，将方法名、参数类型、参数值等信息封装成一个 RPC 请求对象，并按照指定的序列化协议（如 Protobuf 等）将其转化为字节流，也就是序列化
  3. 真正发送请求前，RPC 框架通过服务发现机制（通常从注册中心获取库存服务实例列表）+ 负载均衡算法 选择一个目标实例，然后将序列化后的字节流通过网络发送到库存服务，底层通常基于 TCP、HTTP/2 等协议完成传输
  4. 库存服务收到字节流后，首先进行反序列化，解析出要调用的方法和参数，执行真正的库存扣减逻辑
  5. 库存服务执行完成后，将执行结果封装成响应对象并进行序列化，再通过网络返回给订单服务
  6. 订单服务中的库存服务代理收到结果后再反序列化解析执行结果，封装成本地对象返回

RPC 框架 = 代理 + 序列化 + 服务发现与负载均衡 + 网络传输 + 反序列化

2.2.3 常见的 RPC 框架

常见的 RPC 框架有 gRPC、Dubbo、Thrift 等。

  • gRPC 是 google 开源的框架，序列化和反序列化性能较高
  • Dubbo 是阿里开源的 RPC 框架
  • Thrift 是 FaceBook 开源的框架

2.3 注册中心

2.3.1 为什么要有注册中心

随着电商分布式服务的不断扩展，有些服务不断扩张，可能需要水平扩张。比如订单服务需要新增服务器扩展性能，那么就有一个新的域名、端口要维护，并且系统中其他服务都得知道这个新服务的存在，那么其他服务都得新增配置并重启，这显然是不合理的。

于是就出现了注册中心，各个服务之间如果有依赖关系，可以通过注册中心感知到其他服务的存在，达到各个服务之间依赖关系的解耦。

2.3.2 注册中心的核心思想

注册中心的核心其实就是将服务之间的存续依赖的维护从各个服务自身集中到一起用一个中间件管理，这个中间件我们就称之为注册中心。

  • 服务启动后，会向服务注册中心注册服务，暴露自己的地址和端口，注册中心更新服务列表，并推送通知订阅的服务

  • 服务启动时也会向注册中心请求可用的服务，并缓存再本地

    缓存有两个作用：

    1. 减少对注册中心的请求，提高响应速度
    2. 提高可用性，注册中心宕机不影响正常的服务调用

  • 基于本地缓存调用其他服务

2.3.3 常见的注册中心组件

目前微服务的解决方案中，有三种常见的服务发现组件：Eureka、Nacos、ZooKeeper

ZooKeeper

主要应用在 Dubbo 的注册中心实现，由于 Dubbo 在国内微服务的盛行，Dubbo + ZooKeeper 成为经典的服务化方案，也使得 ZooKeeper 成为注册中心的经典解决方案。

ZooKeeper 是树形的目录服务，支持消息的变更推送。

  • 注册服务，在 ZooKeeper 上注册服务，以 com.example.demoServer 为例，其实就是在对应目录下新建节点并记录自己的路由信息（URL），比如在 /dubbo/com.example.demoServer/providers/xxx.com
  • 订阅服务，请求 ZooKeeper 的服务列表，在本地缓存 providers 目录下的信息

2.4 配置中心

2.4.1 为什么要有配置中心？

随着业务的发展，应用系统中的配置越来越多，对于一些经常变动且实时性要求较高的配置，如果采取与服务一起发布的方式进行维护，那么每次配置的变更都需要重新发布服务，非常不方便。

服务的配置可用分为两种：

  • 较固定的配置：这类配置几乎不怎么变动、比较稳定，比如数据库配置、缓存配置等
  • 灵活调整的配置：这类配置经常发生修改，比如一些开关变量（限流降级开关等）、业务白名单等

因此，和注册中心类似的思想，独立出一个中间组件，集中化管理服务的配置，从而解耦服务与具体的配置，这个中间组件就是配置中心。

2.4.2 配置管理如何实现？

分布式配置管理本质上也就是一种推送-订阅模式的应用。配置的应用方是订阅者，推送方是配置管理服务。

  • 客户端发布数据到配置中心
  • 配置中心把配置数据推送到订阅方

一般，配置中心会有一个客户端，供开发者变更配置。

2.4.3 主流的配置中心组件

分布式配置管理组件可用自研，也有一些常见的开源组件，比如 ZooKeeper、携程开源的 Apollo、淘宝的 Diamond、百度的 Disconf 等。

其中 Apollo 版本稳定更新、社区活跃，推荐使用。

2.5 链路追踪

2.5.1 为什么需要链路追踪？

在单体系统中，一次请求的调用路径可以通过本地方法栈清晰追踪。但在分布式服务框架中，一次用户调用可能经过错综复杂的网络调用。

如果其中某一处出现延迟、异常，仅凭单个服务难以还原完整的调用路径。因此，需要一种机制，将分散在各个服务的请求片段串联起来，形成完整的调用链路，提升分布式系统的可观测性和问题定位能力。

2.5.2 链路追踪的基本原理

链路追踪的核心思想是为每一次请求分配一个唯一的 TraceId，并在服务之间调用的过程中进行传递。

每一次服务调用都生成一个 Span，记录调用耗时、调用关系等。

最终这些数据上报到追踪系统，追踪系统根据 TraceId、Span 的调用关系信息生成拓扑结构，并将 Span 中的附加信息放在拓扑节点上，帮助开发者迅速定位问题；也可以做一些数据分析的事情。

2.5.3 常见的链路追踪组件

常见的链路追踪组件包括：

  • Google Dapper：Google 的闭源链路追踪系统
  • Zipkin：Twitter 的开源追踪系统，借鉴 google 的 Dapper 的设计
  • EagleEye：阿里的鹰眼，是 Dapper 在阿里内部的实现，闭源系统

3. 架构导航图

单体服务拆分成分布式服务，面临 5 大问题，充分采用 “引入中间件” 的哲学解决，最后逐渐构建经典的分布式服务的组织架构。

  • API 网关：统一管理外部流量，解耦外部流量与内部通信，并作为一个切面进行鉴权、限流、降级、熔断、路由等工作
  • RPC 框架：提供高性能的网络通信方式，用于分布式服务内部的通信交互
  • 注册中心：集中管理服务的域名、端口等信息，解耦各个服务之间的依赖
  • 配置中心：集中管理管理服务的配置中心，解耦服务与服务具体的配置
  • 链路追踪：将分散在各个服务中的调用收集整合，形成完整的调用跟踪链，提供问题追踪、数据分析的功能

二、微服务框架选型：Spring Cloud vs Dubbo

（一）Dubbo

Dubbo 是阿里开源的分布式服务框架，目的是提供高性能的远程服务调用以及一些服务治理的功能。

总体架构分为 5 个角色：

  • Register：服务注册与服务发现中心

  • Consumer：调用远程服务的服务消费方

  • Provider：提供远程服务的服务提供方

    一个服务节点可以既是 Consumer 又是 Provider

  • Container：服务运行的容器

  • Monitor：Dubbo 服务调用的控制台，用于统计和管理服务的调用信息

生产环境使用 Dubbo 组件实现服务调用，需要强依赖 ZooKeeper 注册中心；如果要实现服务治理的周边功能，比如配置中心、服务跟踪等，则需要集成其他组件的支持。

（二）Spring Cloud

Spring Cloud 是基于 Spring Boot 的微服务解决方案集合，是一系列的组件，为微服务开发提供了一整套完整的工具链，包括服务发现、配置管理、API 网关、限流熔断组件、调用跟踪组件等。

（三）Spring Cloud 和 Dubbo 对比

总体来说，Spring Cloud 提供了开箱即用、高度扩展性的微服务工具集生态，使用较简单，模块间耦合度低。Dubbo 侧重提供高性能 RPC 通信的微服务框架，对于服务治理的功能需要结合其他组件比如 ZooKeeper 等来实现，一般大型企业内部有很多自研组件，会结合 Dubbo 做微服务。
