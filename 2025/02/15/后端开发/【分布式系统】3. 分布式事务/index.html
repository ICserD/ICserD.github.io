一、分布式事务概述

（一）为什么有分布式事务？

分布式事务是随着分布式系统的诞生而诞生的，分布式系统的设计往往涉及到系统拆分，而系统拆分有常常涉及到服务拆分和存储拆分，正是服务和存储的拆分，催生了分布式事务的出现。

分布式系统下，系统的服务被拆成多个不同的服务，各个不同的服务又有不同的持久化层，有时完成一个请求需要经过多个服务的状态变更，业务上常常要求多个服务的状态变更保证业务逻辑一致性，这时候就需要分布式事务了。

拿电商系统的下单场景举例，涉及到的系统包括订单服务、库存服务、会员服务、支付服务等；用户的下单操作同时依赖这几个服务，如果有一个服务失败，下单也就必须是失败，否则就出大问题了。

（二）什么是事务？

事务的本质是将对一组数据的操作进行逻辑封装，使其作为一个整体执行，并满足 ACID 特性。

  • A，Atomicity：原子性，一组操作要么都完成、要么都回滚
  • C，Consistence：一致性，事务执行前后必须保证数据逻辑约束，比如 A 转给 B 必须是 A 余额减少和 B 余额增加，并且金额相等
  • I，Isolation：隔离性，不同事务之间互不影响
  • D，Durability：持久性，事务提交后，数据不会因为崩溃丢失

（三）本地事务 vs 分布式事务

本地事务、分布式事务，本质区别在于是否跨越多个独立资源管理器

注意，独立资源管理器并不等同于机器资源，比如 MySQL 其实分为 server 层和 engine 层，也需要用分布式事务保证 server 层的 binlog 和 engine 层的 redo log 的事务特性。

  • 本地事务：所有数据操作都由同一个资源管理器控制，并在该资源内部保证 ACID 特性

  • 分布式事务：事务中的操作分散在多个独立的资源，需要通过协调机制（2PC、3PC、TCC 等）来保证整体一致性

    分布式事务中，ACID 是目标追求，但通常完全实现 ACID 成本较高，如果不是业务需要，一般采用最终一致性或补偿机制代替强一致性的分布式事务

二、常见的分布式事务解决方案

分布式事务的解决方案，常见的有两阶段提交（2PC）、三阶段提交（3PC）、TCC 分段提交以及基于消息队列的最终一致性设计。

2PC 是经典的分布式事务解决方案，适用于强一致的场景。3PC 是基于 2PC 的优化，核心是超时自抉择机制，但是也存在超时时间难以确定和不确定性的安全问题，因此很少在工程实践中使用。TCC 适用于高可用、不追求强一致的事务场景。

在工程实践中，一般来说：

  • 强一致需求：2PC + 日志/恢复/TM 高可用（共识机制保证 TM 集群一致性，又保证高可用）来实现
  • 高可用需求：TCC 或基于消息队列的最终一致性方案

这些都需要进行掌握，下面进行逐一介绍。

（一）核心思想

分布式事务主要解决的是多个节点的事务问题，如果我们把整个事务分治到每一个节点，那么其实就是需要保证各个节点的事务要么都提交、要么都回滚。

这也是蚂蚁金服开源分布式事务组件 Seata，也就是 Fescar 的核心思想。

但是这种做法存在一个问题，节点不知道其他节点的状态，无法决定是提交还是回滚。此时可以引入一个协调者，协调各个节点的统一行动，这有点像拜占庭问题中各个小国得到一个信任的领头国。

协调者在此处的作用是，每个节点可以从协调者这里知道其他节点是否都已经可以提交，明确都可以提交后才提交。

（二）两阶段提交（2PC）

两阶段提交就是分布式事务的一个经典实现方式，核心思想就是通过一个协调者协调各个节点，使得分布在不同节点的操作具备逻辑一致性。

两阶段提交可以总结为两种角色、两个阶段。角色通俗来说就是协调者节点和参与者节点， 两个阶段分别为提交请求阶段、提交阶段。

两种角色

工程实践中，将角色抽象成事务管理者（Transaction Manager）和资源管理者（Resources Manager），其实分别就对应着协调者和参与者。

两个阶段

分别为准备阶段和提交阶段，核心思想是确认所有节点都准备好之后才能提交，否则全部回滚。下面详细介绍两阶段的过程。

1. 准备阶段（prepare）

  • 收到客户端请求后，TM 向所有 RM 发送 prepare 请求
  • RM 开启本地事务、锁资源、执行所有操作、写日志，不提交，执行完后，返回 yes/no
  • TM 一旦收到 no，返回给客户端处理失败；否则 TM 收到所有 yes 后进入 commit 阶段

2. 提交阶段（commit）

只有当 TM 收到所有 RM 的 yes 才进入这个阶段。

  • TM 向所有 RM 节点发送 commit 请求
  • RM 节点本地提交事务，返回 ack
  • TM 收到所有 RM 节点的 ack 后，返回给客户端处理成功

2.1 为什么提交阶段不存在 RM 节点返回 no 的分类讨论？

  • 进入提交阶段后，各个 RM 已经在本地执行了事务并写入日志，这些操作已经成为系统事实，commit 只是决定是否对外可见，不存在真正的提交失败问题
  • 可能的提交失败情况，其实是网络分区的影响导致有些节点等不到是否可以可以提交的通知，但是这些操作也不会丢失，只要有通知，就能提交成功

3. 两阶段提交存在的问题

两阶段提交存在明显的问题，下面逐一介绍。

3.1 资源被同步阻塞（被锁住）

在准备阶段中，所有参与者执行事务的时候需要锁住资源，避免并发问题，会阻塞住所有第三方的相同资源的访问。

3.2 TM 存在单点故障问题（致命阻塞）

事务管理者/协调者作为协调各个节点的组织者在系统中起着至关重要的作用，所有节点都依赖于 TM 而正常工作，一旦 TM 宕机，系统事务失效（不可用）。

分析一下 TM 在不同时期宕机产生的影响：

  1. 接收客户端请求后、发送 prepare 通知前：此时 RM 没执行事务，不锁资源，TM 宕机后仅影响客户端，客户端会长时间收不到响应
  2. 发送 prepare 通知后：有些 RM （prepare 阶段）或者所有 RM （commit 阶段）已经执行事务，锁住了资源，等待 TM 通知提交；此时 TM 宕机不仅影响客户端，还会导致部分 RM 阻塞等待

4. 总结

两阶段提交在理论上是可以实现强一致性的事务的，但是存在严重的问题，后面 3PC 是基于 2PC 的优化，解决了 2PC 的部分问题，但大体思想基本一致。

（三）三阶段提交（3PC）

2PC 存在和核心问题是RM 在 prepare 后如果拿不到 TM 的最终决策，会一直阻塞（锁资源、无法提交或无法回滚）。

3PC 的改进思路是：

  • 在“是否可以提交”之前引入一个新阶段，基于超时机制校验一下 RM 是否具备进入 prepare 状态的条件（不进入 prepare 状态、不开启事务、不执行）

  • 如果所有 RM 都具备，才进入正常的 prepare 阶段，大大降低 TM 宕机的影响

    前面分析过，TM 如果在 RM 进入 prepare 后宕机，就会阻塞至少部分 RM，产生较大的影响

3PC 是基于 2PC 的改良方案，角色和 2PC 一样，阶段分为三个阶段。下面进行介绍。

1. canCommit 阶段（询问是否可以提交）

  • 客户端发起事务请求，TM 向所有节点发送 canCommit 请求

  • RM 检查自己是否有 commit 的条件，比如资源是否充足、是否满足事务的约束条件等，然后 RM 返回 yes/no

    RM 在这一阶段，不会开启事务、不会执行事务、不会锁资源，仅做检查，因此即使 TM 挂了对系统也没太大影响

  • 一旦 TM 收到任意一个 no，直接响应客户端处理失败；否则 TM 收到所有 yes，进入 preCommit 阶段

2. preCommit 阶段（预提交：RM 进入提交状态）

只有当所有 RM 返回 yes，才进入该阶段。

  • TM 向所有 RM 发送 preCommit 请求
  • RM 开启事务、锁资源、执行事务、不提交；执行完后返回 yes/no
  • TM 收到任意一个 no，响应客户端处理失败；否则 TM 收到所有 yes，进入 commit 阶段

3. commit 阶段（最终提交）

只有当所有 RM 返回 yes，才进入该阶段。

  • TM 向所有 RM 发送 commit 请求
  • RM 在本地进行事务的提交，返回 ack
  • TM 收到所有 ack 后，返回客户端处理成功

4. 3PC 的优化点

3PC 相较于 2PC，最大的优化就是降低了阻塞的概率，以及使得阻塞能够在有限时间内结束。

4.1 基于超时机制的自抉择规则

这是 3PC 的核心优化。3PC 为了减少阻塞的影响，采用超时自抉择规则，使得阻塞能在有限时间内结束。

  • 如果 RM 在 canCommit 之后超时没等到 TM，直接 abort，本地回滚

  • 如果 RM 在 preCommit 之后超时没等到 TM，倾向于 commit，本地自己提交

    这也是 3PC 的争议点，自提交的规则使得系统存在不确定的安全问题

4.2 新增 canCommit 阶段降低 rollback 的可能

在 preCommit 前新增 canCommit 阶段，也就是在 RM 开启事务前先确认是否有条件进行 commit，降低了开启事务后再 rollback 的可能。

5. 3PC 存在的问题

3PC 相较于 2PC 最大的优化就是减少阻塞的概率和降低阻塞的影响，但这是基于“超时自抉择”机制完成的。

这种做法存在极大的缺陷：

  1. 强依赖网络延迟有上限这一假设，难以设计出满足业务需求的超时时间
  2. 自提交机制带来不确定性的不一致影响

（四）TCC，Try、Confirm/Cancel

2PC 为代表的分布式事务解决方案是跨库跨表的大粒度事务，遇到复杂、长链业务的事务需求时，可能会导致长时间阻塞，性能很低，无法满足业务需求。

TCC 提出一种新的事务模型，基于业务层面的事务定义，锁粒度完全由业务控制，目的是解决复杂的分布式事务中，跨库跨表的大粒度资源锁定导致的性能低的问题。

TCC 把事务运行过程分为 Try、Confirm/Cancel 两个阶段，每个阶段的事务逻辑由业务代码控制，避免了长事务，可以获得更高、更可控的性能，本质上是 TCC 的思想与 2PC 类似，都分阶段决定事务是否最终提交，但 TCC 是在业务层实现的补偿型分布式事务方案。

下面先介绍 TCC 的思路、流程，最后通过一个例子体会 TCC 的实现方式，最后总结归纳 TCC 的优势和存在的问题。

1. TCC 的核心思想

TCC 的核心思想是将跨服务的状态变更拆分为“资源预占（Try）”、“最终提交（Confirm）”和“补偿回滚（Cancel）”三个部分，通过业务层状态控制实现分布式事务的一致性。

其中最核心的就是资源预占，通过资源预占对实际资源进行实际的占用或冻结，使得资源在最终决策前不会被其他事务使用，保证 confirm 阶段尽量不会失败。

2. TCC 流程 —— 两阶段

TCC 是一种基于业务补偿的分布式事务方案，其思想类似 2PC，都是分阶段决定事务是否最终提交，分为 Try、Confirm/Cancel 阶段。

Try 阶段（资源预留）

  • 客户端发起事务请求，服务端执行逻辑、调用各个其他服务的 Try 接口

  • 其他服务收到 Try 请求后：

    • 进行业务检查（请求是否合理、资源是否充足、是否满足业务约束等）
    • 进行事务预处理，冻结需要操作的资源（比如先记录下来要扣多少库存、要减少多少余额等，冻结库存、冻结余额）

  • 最后返回 yes/no

  • 如果有响应 no 的节点，Try 阶段直接失败，进入 Cancel 流程

    为什么这里不进行重试？

Confirm/Cancel 阶段（正式提交/补偿回滚）

如果 Try 阶段失败或事务主动 Cancel，进入 Cancel 的流程：

  • 服务端调用各服务的 Cancel 接口
  • 释放冻结的资源，回滚预处理逻辑
  • 响应客户端
  • 如果执行过程中出错，则进行重试，如果重试失败则触发告警，人工干预兜底

如果 Try 阶段成功，进入 Confirm 的流程：

  • 服务器调用 Confirm 接口
  • 基于冻结资源进行操作，比如库存正式扣减、余额正式扣减
  • 释放冻结资源标记
  • 响应客户端
  • 如果执行过程中出错，则进行重试，如果重试失败则触发告警，人工干预兜底

由于 Confirm/Cancel 阶段通过重试来处理失败的情况，因此要保证 Confirm/Cancel 接口的幂等性。

这里其实涉及到幂等性设计了，再进一步思考，其实分布式系统下几乎所有的非幂等接口（POST/PUT/DEL 等）都需要保证幂等性，因为分布式系统下各个系统之间的交互是基于网络的，由于网络的不稳定性，同一接口的多次请求是几乎不可避免的。

而对于需要重试兜底的接口，更加需要保证幂等性。

3. 真实业务场景分析 TCC

以电商场景的支付业务演示 TCC 如何实现，在电商支付场景中，用户在支付之后，一般伴随着订单状态更新、账户余额扣件、库存扣减和账户积分增加。

3.1 业务逻辑拆解

我们把订单业务拆解成下面几个步骤：

  1. 更新订单状态
  2. 账户余额扣减
  3. 库存扣减
  4. 账户积分增加

显然，如果上面四个步骤不满足事务约束，出现不一致，可能会出现已经下单了但是没发货、超卖、积分没增加等问题，这个在业务上是不能接受的，会出现大量的客诉以及难以估量的经济损失。

3.2 业务系统 TCC 改造

应用 TCC 实现事务，需要对业务系统进行侵入性改造，每一个步骤都需要抽象 Try、Confirm、Cancel 阶段。

Try 操作

try 操作的核心是冻结资源，而不是直接扣减资源。下面分别分析各个服务针对 try 如何冻结资源：

  • 订单服务：订单状态更新为 updating，如果当前订单状态不是 toPay 则 Try 失败
  • 账户服务：假设要扣除数量为 toDeduct，引入冻结字段 frozenAmount，availableAmount = balance - frozenAmount；当 availableAmount >= toDeduct 时，执行 frozenAmount += toDeduct，否则 Try 失败
  • 库存服务：加入要扣除数量为 toDeduct，引入冻结字段 frozenStock，availableStock = balance - frozenStock；当 availableAmount >= toDeduct，执行 frozenAmount += toDeduct，否则 Try 失败

Confirm 操作

当所有服务的 Try 都成功后，系统进入 Confirm 阶段。Confirm 操作基于冻结资源进行最终提交：

  • 订单服务中，订单状态更新为 paid

  • 账户服务中，balance -= toDeduct、frozenAmount -= toDeduct

  • 库存服务中，balance -= toDeduct、frozenAmount -= toDeduct

Cancel 操作

当 try 阶段任意服务失败，或事务需要主动终止时，进入 Cancel 阶段。

其实 Cancel 阶段就类似于在业务层面设计了一个等价于回滚的补偿机制。

Cancel 操作主要是在 try 失败后，释放冻结资源：

  • 订单服务：订单状态恢复为 toPay
  • 库存服务：frozenAmount -= toDeduct
  • 账户服务：frozenAmount -= toDeduct

约束

Confirm/Cancel 操作一旦执行，不允许回滚，因此必须保证：

  • 失败时持续重试
  • 接口幂等
  • 必要时人工干预

4. TCC 的优缺点分析

  • TCC 在业务执行的时候，只操作预留的资源，几乎不会涉及到锁和资源的争用，具有很高的性能潜力

  • 但是 TCC 的业务侵入性较高，在使用上有较大的弊端，需要投入较大的编码成本，以及涉及到一些技术可控性约束

    如何理解这里的技术可控性约束？比如要实现 TCC 可能要修改银行收银系统，但是没有权限操作，对方也不会开放权限和数据给你。

  • 在实际业务中，一般不完全依靠裸编码实现 TCC，而是基于某些分布式事务中间件完成，比如 Seata

三、XA 规范 —— 以 MySQL 为例

（一）XA 规范简介

XA 是由 X/Open 组织提出的分布式事务规范，XA 规范主要定义了事务协调者（TM）和资源管理器（RM）之间的接口；XA 事务是基于两阶段提交的。

  • TM：事务管理者，也就是协调者，管理事务的生命周期，在 prepare 阶段协调 RM 执行事务但不提交；在 commit 阶段协调 RM 提交或回滚事务
  • RM：资源管理者，也就是参与者，负责接受 TM 的信号做出资源操作

XA 规范定义的是 TM 和 RM 的接口，也就是 TM 和 RM 的交互规范。

（二）XA 事务的执行流程

XA 事务的流程就是两阶段提交的流程，分为 prepare 阶段和 commit 阶段。

详细参见2PC

（三）MySQL 如何实现 XA？

MySQL 中的 XA 事务有两种情况：内部 XA 和外部 XA；区别在于事务发生在单机服务器上还是发生在多个服务节点上。

1. 外部 XA

MySQL 的外部 XA，其实就是典型的 2PC，解决分布式系统下各个节点的事务一致性问题，只不过这些节点变成了 MySQL 服务。

MySQL 提供了实现 XA 事务的命令，支持XA START/END/PREPARE/COMMIT这些 SQL 语句，通过这些命令可以完成分布式 XA 事务。

MySQL 官方提供的 XA 命令用法

外部 XA 应用场景一般是跨多个 MySQL 实例的分布式事务，需要应用层作为协调者（TM），比如我们写业务代码，在代码中决定提交还是回滚，并且在崩溃时进行恢复。

2. 内部 XA

一般为了 MySQL 的高可用，会采用多机部署的方式部署 MySQL 服务，这就涉及到了主从同步。主从同步一般的做法是从库订阅主库的 binlog 日志。

MySQL 服务分为 Server 层和 Engine 层，Server 层有 binlog 日志，主要用于主从复制，记录对数据库的状态变更操作，比如写数据、变更表结构等。Engine 层有 redo log 和 undo log，undo log 主要用于事务回滚，记录状态变更前的旧值和变更的操作、redo log 用于崩溃恢复，记录对数据库状态的变更操作、记录对脏页的修改。

不难看出 Server 层的 bin log 和 Engine 层的 redo log 其实都是记录对数据库的变更操作，区别在于 bin log 记录的是全量日志，主要用于主从同步；redo log 记录的是增量日志，只记录对脏页的修改，如果脏页落盘则日志可以被擦除。但逻辑上 bin log 和 redo log 要保持一致。

在 XA 事务出现以前，bin log 和 redo log 并不是原子的，bin log 在 server 层、redo log 在 engine 层，不难保证其原子性，因此可能出现数据不一致。

  • 对于主节点来说，假设 bin log 写了，redo log 没写，然后主节点宕机，将导致主节点本地恢复后丢失一些状态变更，而从节点提供 bin log 却保留了这些状态，造成数据不一致
  • 假设 bin log 没写，redo log 写了，主节点宕机，那么主节点恢复后，本地能找回状态但是从节点丢失状态变更

2.1 内部 XA 如何实现

内部 XA 也是 2PC 的思想，分为准备阶段（prepare）和提交阶段（commit），用于保证 InnoDB 的 redo log 与 Server 层的 bin log 在崩溃场景下的一致性。我们可以把 Server 层看成 TM，Engine 层看成 RM。

2.1.1 准备阶段（prepare）

客户端请求到来后，Server 层先生成一个 XID 唯一标识该事务，然后作为参数调用 InnoDB 层的 prepare 接口执行操作：

  • 修改数据页
  • 写 undo log、写 redo log
  • 在 redo log 中写入包含 XID 的 prepare 记录，将事务标记为 prepared 状态

若上述操作都成功，则 prepare 接口返回成功；否则返回失败，Server 将终止事务并执行回滚，不写 bin log

2.1.2 提交阶段（commit）

如果 InnoDB 返回成功，进入提交阶段：

  • Server 层根据事务变更生成 bin log，将对应的 XID 写入 bin log，持久化到磁盘
  • bin log 写入成功后，Server 层调用 InnoDB 的 commit 接口，XID 作为参数
  • InnoDB 在 redo log 对应的日志下写入 commit 标记，事务正式提交
2.1.3 崩溃恢复过程

如果 InnoDB 的 redo log 还没刷盘就崩溃了，对系统无影响，此时 bin log 也没写。

如果 InnoDB 的 redo log 刷盘后、bin log 刷盘前崩溃，恢复后 InnoDB 重新扫描 redo log 发现有 prepare 的日志未提交，根据其 XID 去查找 Server 层的 bin log 中是否存在该 XID，如果存在则说明该事务也写入 bin log 了，执行 commit；否则说明事务未完成，没写入 bin log，通过 undo log 进行回滚。

通过 XID，redo log 和 bin log 可以建立映射关系，保持一致性。
