【分布式系统】5. 分布式存储（上）

一、分布式存储概述

分布式系统是软件和硬件都分布在不同的网络节点上，各个节点相互协调和通信，对外提供统一的服务的系统。

分布式系统集中体现了“分治”的思想，包括服务的拆分、计算的拆分和存储的拆分。前面我们主要介绍了服务的拆分，接下来我们介绍存储的拆分，也就是分布式存储。

分布式存储涉及到的技术非常广泛，本文仅抓住一些重点、热点进行梳理，包括读写分离、分库分表，以及分库分表带来的问题如何解决。

二、读写分离

（一）什么是读写分离？

在很多业务场景中，对数据库的读请求远远多于写请求，如果读写请求都打到同一个数据库，那么会出现一些问题：

  1. 写请求会锁表或锁行，阻塞部分读请求
  2. 大量请求打到同一个库，性能降低

此时我们可以采取读写分离的策略，数据库采用主从复制架构，主库处理写请求、从库处理读请求，达到分散读请求、提高并发读性能的效果。

（二）主从复制技术

读写分离依赖数据库的主从复制架构，下面介绍 MySQL 的主从复制技术。

MySQL 中的 Server 层有一类日志为 bin log，记录着全量的对数据库的写操作，也就是数据库状态变更的历史，通过 bin log 日志可以备份出一个完全相同的数据库。

1. bin log 日志格式

bin log 有三种日志格式：

  • statement 格式，记录 SQL 语句，其他 DB 通过在本地回放该类型的 bin log 即可完成备份
    • 优点：日志数量少
    • 缺点：备份过程慢；存在动态函数问题，比如 random、uuid 的生成
  • Row 格式，记录每一行的修改操作
    • 优点：不存在动态函数问题，备份过程快
    • 缺点：每一处修改都会被记录，日志数量多、占用空间大
  • 混合模式，包含 statement 和 row 的格式

2. 主从复制过程

bin log 日志一般用于数据库备份，主从复制其实就是从库实时备份主库的过程。主从复制过程如下：

  • 主库将数据库的变更写入 bin log 日志，从库连接主库之后，主库创建一个 log dump 线程，用于发送 bin log 内容
  • 从库开启主从复制后，创建一个 IO 线程连接主库，请求主库的 bin log，IO 线程接收到主库 log dump 线程发来的更新后，将读到的内容写入本地 relay 日志文件中
  • 同时，从库会有一个 SQL 线程负责读取 relay 日志内容，解析并回放 relay 日志以备份主库数据

3. 读写分离带来的问题

3.1 主从延迟

写主库后，主库同步到从库往往需要一定的时间，这一段时间存在主从不一致，这一段窗口期也就称为主从延迟。

一般根据业务需求不同，主从延迟的解决方案也就不同。

强一致性业务 —— 绕过延迟、强制读主库

对于强一致性业务，比如下单之后，主库已经写了用户状态是已支付，从库却是未支付，用户刷新一下发现自己还没支付，通常在业务中不可接受。

此时可以采取写后强制读主库来解决。

非强一致业务 —— 忽略延迟或减少延迟

对于一些商品列表展示等不追求强一致的业务，可以忽略对主从延迟的处理，业务上一般可以接受主从延迟的影响。

可以记录并分析主从延迟的时间，TP99 下的时延大概是多少，看看业务上是否能接受，不能接受的话就考虑将延迟降低到可以接受的范围即可。

三、分库分表

（一）什么是分库分表？

分库分表是数据库高可用的另一大杀手锏，主要应对海量的数据存储与处理。

当单个数据库/数据表的数据量/请求量特别庞大时，单库/单表的性能大大下降时，就需要考虑将数据分开存储在多个不同的数据库或数据表中，这就是分库分表。

为什么分库分表是必要的呢？这其实是单机存储的瓶颈决定的。单机存储下：

  • 连接有限
  • 存储容量有限
  • 处理性能有限

导致了存储拆分的必然，通过拆分的方式突破单机瓶颈。

（二）如何分库分表？

1. 什么时候分库？什么时候分表？

《阿里巴巴 Java 开发手册》的 MySQL 数据库建表规约中推荐如下：

  • “【推荐】单表行数超过500万行或者单表容量超过2GB，才推荐进行分库分表。
    说明：如果预计三年后的数据量根本达不到这个级别，请不要在创建表时就分库分表。”

分库和分表是两个独立的概念，总的来说，分库和分表的应用场景不太一样：

  • 分库：并发量大时必须分库，分表无法增加并发量；在微服务拆分的场景下，一般也会分库，不同服务的表放在不同库

    MySQL 有命令查看最大连接数，一般来说最大连接数在 100 ～ 150

  • 分表：数据存储量大时进行分表，避免单表查询瓶颈

2. 分库分表的常见思路

分库分表的核心思想其实就是“分治、分片”，对于分片，最常见的有两种划分方式 —— 水平划分、垂直划分。

2.1 垂直划分

垂直划分的核心思想是基于分片规则将一个大的数据集划分为异构的小数据集。

在分库分表中，垂直划分分为垂直分表和垂直分库。

  • 垂直分库：在微服务拆分中最为常见，根据业务边界将不同服务的数据放在同一个库，做到专库专用，比如订单服务用订单库

  • 垂直分表：一般用于一个表字段耦合的场景，当一个表有很多字段并且不同业务基于这些字段耦合在一起，可以考虑垂直分表

    比如有一个商品表 goods(id, name, img, price, stock, describe)，发现其实商品描述 describe 字段的访问频率不高，但空间占用大，此时就可以进行垂直分表，将描述字段单独拆分出来作为一张扩展表，主表和扩展表之间提供 goods_id 关联：

    • 主表：goods_master(id, name, img, price, stock)
    • 扩展表：goods_describe(id, goods_id, describe)

2.2 水平划分

水平分片的核心思想是基于分片规则将一个大的数据集分为同构的小数据集。

在分库分表中，水平分片分为水平分库和水平分表。

  • 水平分库：按照一定的规则将单表的数据子集划分到不同的数据库上，每个数据库都有相同的表，只是存储的数据集不同
  • 水平分表：按照一定的规则将单表的数据子集划分到同一个数据库的不同子表中，每个子表的结构完全相同（表名不同），存储的数据集不同

（三）分片算法

前面我们讲到了在分库分表中的划分思想，大方向上看就是水平划分和垂直划分。

水平划分和垂直划分是划分的方向，划分的核心则是划分规则，也就是划分算法，决定着一条数据会去到哪一个库、哪一张表。

一般来说，有三种划分算法：范围分片、哈希分片、查表分片。

1. 范围分片

选择一个维度进行范围划分。一般这个维度可以是时间、地域、大小。

  • 时间维度：比如订单表按照订单时间划分
  • 地域维度：如果业务涉及到的地域比较广，比如全国性的，可以按照地域划分，比如按照省份划分
  • 大小维度：比如 0 ～ 500w 的 id 放在 table_1、501w ~ 1000w 的 id 放在 table_2…

优点

  • 水平扩展方便，直接新增一个库、一个表即可，无需进行数据迁移
  • 单表数量可控，也就是一段时间、一个省份或一个 id 范围

缺点

  • 存在热点数据问题，也就是可能有些库表的数据访问量特别大，有些特别小

2. 哈希分片

2.1 普通哈希

哈希分片是一种常见的分片方式，对关键字段取模即可，除数是分片个数。

比如订单表要分成 3 个库或者 3 个表，则可以用 id % 3 来决定一条数据去哪个库或哪个表。

  • 优点：数据比较均匀，出现热点数据的概率较小
  • 缺点：水平扩容复杂，集群伸缩性较差；由于哈希算法依赖于提前约定好要分多个个片，如果需要改动分片个数或者某些分片不可用，则需要所有数据重新进行哈希，成本较大

2.2 一致性哈希

2.2.1 一致性哈希算法原理

一致性哈希是普通哈希的改进算法，主要是为了优化普通哈希在伸缩性上的局限性，可以更好地处理分片数量的变化。

一致性哈希中，取模的除数是 231−12^{31} - 1231−1，无论新增还是减少分盘，都不改变这个基数，以此降低分片变化的影响；也就是说，无论分片数怎么变化，都直接将数据分散到 231−12^{31} - 1231−1 个点上；我们把这 231−12^{31} - 1231−1 个点看成一个环，这个环被称为哈希环。

一致性哈希的过程，实际上就是在哈希环上找分片的过程，一般分为两步：

  1. 分片的哈希，如果一个分片是一个机器，那么可以用这个机器的 IP 对 231−12^{31} - 1231−1 取模，得到该分片在哈希环上的位置
  2. 数据的哈希，用数据的对 231−12^{31} - 1231−1 取模，得到这个数据在哈希环上的位置

数据如何知道要放在哪个分片？数据和分片的哈希值并不一定相同，可能分布在环上的不同位置，因此当数据进行哈希后，顺时针寻找分片，找到的第一个分片就是该数据存储的分片。

2.2.2 一致性哈希好在哪？

一致性哈希的主要优势是在分片伸缩性上，分片的增加或减少仅影响部分分片，也就是部分分片需要进行数据迁移，而对于普通哈希来说，分片的增加或减少可能会影响所有分片。

为了便于理解，通过模拟的方式说明一致性哈希的核心优势 —— 分片伸缩性强。

假设新增分片

下图中节点 D 是新增的分片，那么所有哈希值范围在节点 A 到节点 D 这一段的数据，都需要从分片 B 迁移到分片 D，其他不需要变动，也就是仅影响节点 B。

假设减少分片

下图中删除分片 A，那么所有哈希值范围在分片 C 到分片 A 的数据，都需要从分片 A 迁移到分片 B，也就是仅影响分片 A 和分片 B。

2.2.3 一致性哈希的缺点

一致性哈希表不能保证分片在哈希环上的均匀分布，这可能导致数据热点问题，也就是数据分配不均。

数据分配不均将导致连锁问题，比如大量请求集中在某几个分片、雪崩式扩容等。

比如下图中，大量请求集中打到分片 A；大量数据哈希分片后存储在分片 A，如果分片 A 宕机，大量数据需要从分片 A 迁移到分片 B，如果超过了分片 B 的承受能力可能导致分片 B 也宕机，那么分片 A 和分片 B 的数据都需要迁移到分片 C，引起雪崩式反应。

2.2.4 通过虚拟分片增加均衡度

一致性哈希带来的问题，本质上其实是分片在哈希环上分配不均导致的。因此解决方案是增加分片分布的均衡度。增加节点分布的均匀度，最简单的方式就是增加节点数量，因此通过增加虚分片的方式增加均衡度：

  • 比如设置每个真实分片对应多少虚拟分片

    nginx 中的一致性哈希算法，一个权重为 1 的节点一般含有 160 个虚节点

  • 不再将真实的分片映射到哈希环上，而是将虚拟分片映射到哈希环

  • 然后再将虚拟分片映射到真实分片上

2.2.5 虚拟分片的方法好在哪？

主要有两点好处：

  1. 增加分片均衡度，避免热点数据带来的问题
  2. 分散迁移压力，当节点变化时，会有不同的节点共同分散系统的变化，稳定性更高

3. 查表分片

查表分片是通过预先构建映射关系表来决定数据流向哪一个分片。每次查询数据时，先查分片映射表，看看这个数据在哪个分片，再去对应的分片查真实的数据。

具体怎么建立映射表完全人为定义，灵活性极大。

优点：灵活性高，规则非常灵活

缺点：

  • 对数据量有一定的限制，分片映射表本身就不能太多数据，否则映射表本身就可能成为系统瓶颈
  • 每次查询需要经过至少两次请求，可能会影响性能

（四）分库分表实践

分库分表在业务实现上一般有两种主流模式：代理模式和客户端模式

两种方式的核心区别在于分片逻辑是由应用自己控制，还是由中间件统一控制。

1. 客户端模式

分库分表的逻辑在系统内部实现。

在 Java 开发中，通常以 jar 包的方式提供服务，常见的组件有：

  • ShardingSphere-JDBC
  • 阿里的 TDDL
  • 美团的 MTDDL
  • 自研框架

2. 代理模式

在系统和数据库中间引入一个分库分表中间件，分库分表逻辑由这个中间件统一管理；应用只需要连接代理服务，无需关系数据如何分片。

常见的组件有：

  • 阿里的 MyCAT
  • 美团的 Meituan Altas
  • ShardingSphere-Proxy
