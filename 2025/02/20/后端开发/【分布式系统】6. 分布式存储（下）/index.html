【分布式系统】6. 分布式存储（下）

发表于2025-02-20|更新于2025-02-21|后端开发系统设计
|字数总计:5.1k|阅读时长:16分钟|阅读量:

分库分表本质上是一种存储的拆分，存储拆分后，新的问题随之出现。

本文梳理分库分表后带来的六类常见问题，以及工程上典型的解决思路。

一、分布式事务问题

（一）问题背景

存储拆分后，如果业务上需要保证跨数据库的事务，此时就需要分布式事务了。

比如一个电商系统，分库分表前，订单表、库存表、账户表都在一个数据库，用户下单后需要更改订单状态、扣除库存、增加账户积分和扣除账户余额，在单个 DB 下可以依赖数据库的事务保证一致性。

但服务拆分后，存储也进行了拆分，电商系统拆分出了订单服务、库存服务、账户服务等，此时订单表、库存表、账户表分别在不同的 DB，此时用户的下单操作依赖各个数据库之间的协调来保证事务。

（二）解决方案

分布式事务一般常见的解决方案有四种：

  • 两阶段提交（2PC）
  • 三阶段提交（3PC）
  • TCC
  • 基于消息队列的最终一致性

2PC 是最经典的分布式事务方案，MySQL 的 XA 规范就是基于 2PC 的一种规范，将节点分为 TM 和 RM，由 TM 统一协调所有 RM 执行事务和提交事务。

3PC 是针对 2PC 的改善，新增了一个 canCommit 阶段，减少回滚的概率和影响，但其基于超时的自提交机制带来了分区下的不确定性，一般很少使用。

TCC 是在业务层面实现事务控制的一种强一致的分布式事务方案，核心目标是解决依赖于数据库事务的 2PC/3PC 方案长事务带来的性能问题，通过业务代码灵活控制分布式事务的实现，将分布式事务分为 Try、Confirm/Cancel 三个阶段，核心是通过 Try 阶段冻结资源，Confirm 或 Cancel 阶段基于冻结的资源进行事务操作或回滚，避免了长事务带来的阻塞问题，通常有较高的性能。

基于消息队列的最终一致性方案是通过“本地事务 + 异步消息”保证系统的最终一致，是高并发场景下常用的弱一致性事务解决方案。

  • 若 db1 和 db2 在同一台机器，那么 SQL 语句支持跨库查询 select * from db2.order a join db1.account b on a.account_id = b.id
  • 若 db2 和 db1 不在同一台机器，那么不支持跨库查询

对于跨库的联表查询，即使能查，也存在性能低的问题，我们的方案是尽可能避免跨库的查询操作。

  • 在数据库层面，一般是通过冗余表、冗余字段的方式避免跨库联表查询
  • 在系统层面，可以通过业务代码查询不同的数据集，然后在代码层面进行组装，不依赖数据库的 join

（二）解决方案

1. 冗余表

一般在业务上，我们会抽出一个字典表（数据字典表），将很多表都可能 join 查询的字段结合在一起，然后在每一个数据库都存一张这个字典表。

比如商城系统，分为订单服务、交易服务、库存服务、商品服务…那么此时我们可以做一个架构优化 —— 每个服务的数据库都维护一张商品表（product）：

  • 商品服务的数据中的商品表是主表，更新后通过消息队列（MQ）同步给其他服务
  • 其他服务本地更新自己的 product 表，与主表保持一致

优点：

  1. 提升查询性能，避免跨库联表查询；商品表是各个服务都可能频繁查询的表，比如用户查询订单列表，需要展示商品名称、图片、价格，就需要联合 product 表进行查询，而通过冗余 product 表，可以避免每次都 RPC 请求商品服务来得到 product 表的信息
  2. 降低系统耦合，主要是降低其他服务与商品服务的耦合，如果没有冗余表，那么就需要 RPC 请求商品服务，如果商品服务挂了就会影响其他服务
  3. 减少热点服务压力，商品服务通常是高读流量、热点集中的服务，由于各个服务冗余维护了 product 表，读取商品数据时可以从多个服务中读，这样可以将商品服务的读压力分散到各个服务

缺点：

  1. 带来了数据一致性问题，需要通过 MQ 等机制来维护主表与各个从表的数据一致性

2. 冗余字段

冗余字段的思想和冗余表的思想是一致的；冗余表是通过冗余比较常用的关联表在同一个数据库，避免跨库的联表查询。

冗余字段则是通过冗余常用的关联字段到每一张表，避免联表查询，提升查询性能。

优点：提升查询性能，避免 join 或跨库查询

缺点：有较大的局限性，只适用于冗余字段少的场景，并且可能会对写操作带来麻烦（要维护这些冗余字段）

3. 数据组装

在系统层面，将需要联表查询的变成多次单表查询，然后再通过业务代码进行数据组装。

优点：不依赖数据库层面的关联查询

缺点：内存开销大、性能差

三、非分片字段查询问题

分库分表通常基于某个字段进行划分，如果查询条件不包括这个查询字段，那么可能就难以确定要去哪个分片查询数据。

对于这种问题，一般有三种解决方案：

  1. 维护分片映射表
  2. 基因法
  3. 引入 ES 做查询

下面逐个进行介绍。

（一）分片映射表

顾名思义，新建一个表，维护要查询的数据和具体的分片的关系。

每次查询数据前，先查询分片映射表获取该数据所在的分片，然后再去对应的分片进行查询。

优点：实现简单

缺点：每次查询都需要多查询一次映射表，性能较差；映射表不能过大，否则该表本身可能成为瓶颈

（二）基因法

将分片信息融入到数据的主键 id 的生成逻辑中，即通过数据的 ID 就能够知道该数据在哪个分片！

基因法这个名字非常形象，就好像 ID 携带了分片的基因

优点：性能高；无需额外维护冗余表

缺点：ID 设计复杂度增加

（三）ElasticSearch 组件

对于复杂的查询需求，上述两种方法都比较麻烦。那么我们可以将全部数据同步到 ES 中，所有查询走 ES，回表查询详细信息。

优点：支持复杂查询

缺点：数据需要双写；存在一致性问题；成本增加

四、分布式 ID 问题

（一）问题背景

在分布式存储的环境中，数据分散在不同的机器存储，传统的自增主键无法保证全局唯一性，各个分区生成的 ID 可能会重复；因此，必须设计一种全局的分布式 ID 生成方案来避免跨库的 ID 冲突。

（二）分布式 ID 特性

分布式 ID 必须具备如下特性：

  • 全局唯一
  • 单调递增
  • 高可用：确保任何时候都能生成 ID，否则影响其他业务
  • 高性能：要求高并发下性能优异，不能成为系统瓶颈

（三）分布式 ID 主流方案

分布式 ID 的生成有三类主流的实现方案：

  1. 依赖一定规则本地生成的分布式 ID，优点是性能好，不依赖其他组件
  2. 依赖数据库实现的分布式 ID，优点是实现简单，缺点是数据库可能成为系统瓶颈
  3. 依赖开源组件服务生成分布式 ID，优点是性能好、使用简单，缺点是引入中间件

1. 本地生成的分布式 ID

本地生成的分布式 ID 一般根据一定的算法规则来生成 ID，确保不同机器生成的 ID 不重复。一般有 UUID、雪花 ID 这两类。

1.1 UUID

UUID，Universally Unique Identifier，通用唯一标识符。

UUID 用 32 个 16 进制数表示，也就是要用 128 位来进行存储，依靠一定的算法生成 ID。

格式上是以连字符号分为 8-4-4-4-12 的 5 段，比如：dfae4377-acd7-e7u7-8io9-yhjg8d896yh6

目前业界有 5 种方式实现 UUID，我们不需要了解其中的算法，一般语言会帮我封装好生成 UUID 的库。

优点：生成简单；性能不错；本地生成，没有网络消耗

缺点：可读性差；存储成本高；非单调递增，随机性强

1.2 雪花 ID

雪花算法（Snowflake）是 Twitter 研发的开源的分布式 ID 生成算法，由雪花算法生成的 ID 称为雪花 ID。

1.2.1 雪花 ID 格式

雪花 ID 是用 Long 表示的 ID，占 64 位。按照 1，41，10，12 划分。

  • 最高位保留，默认为 0
  • 随后 41 位表示时间戳，以毫秒为单位，241−1 ms=241−11000∗60∗60∗24∗365≈69.7 year2^{41} - 1\ ms = \frac{2^{41} - 1}{1000 * 60 * 60 * 24 * 365} \approx 69.7 \ year241−1 ms=1000∗60∗60∗24∗365241−1​≈69.7 year，大约能表示接近 70 年的时间戳
  • 10 位机器 ID，同一时间戳，最多可以有 1024 台机器
  • 12 位序列号，同一毫秒的同一台机器最多可以生成 4096 个 ID，并发量高

1.2.2 雪花 ID 优缺点分析

优点：

  • 性能优秀
  • 雪花 ID 单调递增
  • 本地生成，无网络开销

缺点：

  • 强依赖时钟，如果机器上时钟回拨，可能会导致 ID 重复

    时钟回拨：机器上的时间回拨到过去的某个时间

    每一台机器都有自己的本地时钟，依赖 CPU 的晶振脉冲计算出来，随着时间的推移，本地时间和世界真实的时间误差会越来越大，此时需要用 NTP 服务来进行校准。如果本地时钟过快，那么 NTP 服务的校准可能导致时钟的回拨。

3. 基于非关系型数据库主键的分布式 ID

Redis 的 String 数据类型，如果存的是整型数字，可以通过 Incre 命令实现自增。

因此可以利用 Redis 的自增 ID 实现分布式 ID。

一般 Redis 采用集群方式使用，提高性能、可用性，如何避免多个 Redis 机器生成的 ID 重复？

  • 每个机器的设置的起始 ID 不同
  • 自增 ID 的步长大于等于机器数量即可

优点：实现简单，吞吐量高于关系型数据库的分布式 ID 方案

缺点：Redis 集群或实例宕机后，找到最新的 ID 比较困难

4. Leaf 服务

Leaf 是美团开源的分布式 ID 生成服务，名字来源德国数学家莱布尼兹的一句话：“There are no two identical leaves in the world.”，也代表着 Leaf 不会生成重复 ID。

Leaf 实际上就是对基于数据库的号段模式生成 ID 和雪花算法生成 ID 的封装，可以根据场景灵活切换不同的模式。

Leaf 分为 Leaf-segment 模式和 Leaf-snowflake 模式。

4.1 Leaf-segment

基于数据库自增 ID 号段的分布式 ID 生成方案，增加了缓存机制，提前预缓存下一个号段。原理和[号段模式](####2.2 号段模式)一致。

4.2 Leaf-snowflake

Leaf-segment 模式最大的弊端是 ID 过于连续，可能暴露一些商业信息，比如计算今天 12 点得到的 ID 和明天 12 点得到的 ID 的差值可能就能大概估算出一天的订单量。

Leaf 还支持另外一种模式 —— 基于雪花算法的分布式 ID 生成方案 Leaf-flake。

原理和[雪花 ID](####1.2 雪花 ID)一致，但在机器 ID 的生成上依赖于 ZooKeeper 分配的机器 ID。

  • 当 Leaf 节点注册到 ZooKeeper 上，会得到一个 worker ID
  • 于是 Leaf 节点注册完后保存这个 ID 作为雪花 ID 的机器 ID 部分
4.2.1 解决时钟回拨问题

Leaf-snowflake 在生成的时候采用记录最新生成 ID 的时间戳与当前时间戳的对比来避免时钟回拨。

核心思想就是：

  1. 记录本地最新生成的雪花 ID 依赖的时间戳 last_timestamp
  2. 每次生成 ID 时，如果 current_timestamp 小于 last_timestamp，则对比当前时间戳 current_timestamp 与 last_timestamp 的差：
    • 如果差值小与 5ms，则等待 2 倍差值的时间再判断一次 current_timestamp 和 last_timestamp
    • 如果差值大于 5ms，则直接报错，时间差太大
  3. 如果 current_timestamp 大于 last_timestamp，则正常生成 ID

五、分库扩容问题

随着数据规模的增大，原有的分片可能不够，需要扩容；扩容一般是新增分片，新增分片后分片规则也将会改变。

一般有两种做法，停机扩容和非停机扩容。

（一）停机扩容

停机扩容的常见方案：

  1. 预估迁移耗时，发布停机公告
  2. 停止服务（用户无法使用服务），增加分片、更新分片规则
  3. 进行数据迁移
  4. 重新启动服务

互联网行业中几乎不可接受这种方案，扩容期间服务不可用，伤害用户体验，给业务造成损失。

（二）非停机扩容

1. 从库方案/双倍扩容策略

从库方案是利用数据库的主从复制技术进行扩容。下面介绍方案的流程：

  1. 现有的每个数据库新增一个从库，与主库进行同步
  2. 等从库与主库同步好后，断开主从关系，新增的从库全部变成主库，然后更新分片规则完成扩容
  3. 更新分片规则后，有些库的数据部分数据可能不符合当前的分片规则（冗余存储），于是可以后台基于新的分片规则清理不符合条件的数据
  4. 至此，已经完成系统的双倍扩容；还可以为新库增加从库，来提高数据库的可用性

优点：业务无需中断

缺点：扩容数量有限制，必须成倍地扩容

2. 双写策略

双写方案常用于线上数据的迁移，而扩容本质上也是一种数据的迁移，因此可以用双写的方式扩容。

下面介绍双写的步骤：

  1. 准备代码，包括双写代码（同时写旧库和新库）、迁移脚本（旧库向新库的数据迁移）、校验脚本

  2. 开启双写：

    这里可以写旧库，然后通过消息队列将写操作异步作用到新库，提高写性能

    • 插入操作，要写旧库和新库
    • 更新操作，如果新库中没有记录，则将旧库更新后的记录插入新库
    • 删除操作，同时从旧库和新库删除

  3. 旧库和新库的数据迁移：

    • 选择合适的时间戳，该时间戳必须是开启双写后的时间
    • 将旧库中该时间戳以前的所有数据按照新的分片规则迁移到新库

  4. 数据校验：对新库进行数据校验，检查是否有漏或者不一致

  5. 开启双读：逐步增加新库的读流量、减少旧库的读流量，如果有问题及时将流量回滚给旧库

    可以看出，双写策略扩容平滑，比较稳

  6. 关闭旧库的写，迁移完成：当旧库读流量全部稳定迁移到新库，则可以关闭旧库的写、撤销此前的业务入侵代码、脚本，完成扩容

优点：业务不中断扩容，扩容过程更加平滑；可以灵活控制扩容数量

缺点：实现复杂，需要通过校验保证双写一致性

六、跨库分页、排序、函数问题

数据拆分到不同实例存储后，每个分片存储的是部分数据，而对于分页、排序、函数这类计算需要全量数据参与计算。

一般这类问题的解决方案有三种：

  1. 应用层聚合计算：在各个分片分别查询计算，然后在应用层聚合处理各个分片的结果
    • 优点：实现简单
    • 缺点：内存开销大，计算成本高
  2. 利用中间件完成计算：使用 ShardingSphere 等中间件实现
    • 优点：对应用透明，使用简单
    • 缺点：性能开销大，引入额外组件
  3. 业务规避这类计算：尽量避免跨库聚合类的计算
