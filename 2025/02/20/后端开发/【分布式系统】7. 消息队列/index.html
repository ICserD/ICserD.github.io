【分布式系统】6. 消息队列

一、消息队列概述

（一）为什么有消息队列？

在单体架构中，各个模块之间通过方法调用进行通信。当系统扩展到分布式系统后，单体项目被拆分为多个服务，各个服务之间的通信需要通过网络进行通信，此时出现了两种通信方式：RPC、HTTP 通信。

这两种通信方式都是同步调用，会存在如下弊端：

  1. 各个服务在通信是互相耦合，互相阻塞
  2. 单个服务宕机会影响其他与其通信的服务，可能会造成服务雪崩
  3. 底层一般基于 TCP 协议，需要建立 socket 才能通信，仅支持点对点的全双工通信

此时，消息队列出现了，可以理解为消息队列是一种异步的进程间通信方式，支持多对多全双工通信。消息队列并不是服务间通信方式的代替，而是一种补充，要在合适的场景下引入。

（二）消息队列的应用场景

作为一种异步消息缓存与分发组件，消息队列有几种常见的用途，分别是：解耦、异步、削峰、消息分发。

  • 解耦：各个服务之间原本需要进行同步网络通信相互耦合，引入消息队列后，消息从消息队列中读、写，而不是直接与其他服务交互，达到一个解耦合的效果
  • 异步：对于处理时间长、或者不能立即处理的请求，可以考虑使用消息队列进行异步处理
  • 削峰：削峰其实是异步的一个应用，异步化可以增大处理的吞吐量，削峰就是在接口承载能力不足以应对高峰压力的时候采用消息队列将短期高峰流量平摊到较长的一段时间
  • 消息分发：消息队列最本质的应用就是消息分发，并且还可以通过一些手段做到消息分发的可靠性，支持一对多、多对多通信；比如基于消息补偿的分布式事务，就是用消息队列进行消息分发通知其他服务是否完成提交

二、Kafka

本章将梳理一个成熟的消息队列 —— Kafka，我们可以从中体会一个合格的消息队列应该如何实现，并从中汲取一些设计思想。

Kafka 是一个开源的高可用、高性能的消息队列。本节我们通过梳理 Kafka 的工作流程，迅速对 Kafka 有个把握。

消息队列本质上是生产者-消费者模型的实现，对于 Kafka 我们也分为三个部分来看：

  • Producer，生产者，一般是其他的分布式服务，但是对于 Kafka 来说就是生产者客户端；生产者负责把消息投递到 Kafka
  • Consumer，消费者，一般是其他的分布式服务，对于 Kafka 来说是消费者客户端；消费者负责从 Kafka 中拉取消息进行消费
  • Broker，Kafka 服务节点，是我们需要了解的重点；负责接收消息、存储消息、分发消息
    • topic，逻辑上消息分类的标签，用于区分不同的消息
    • partition，物理上存储消息的地方，每个 partition 都是一个有序、不可变的消息队列，一个 topic 可以有多个 partition

（一）核心存储结构

1. Kafka 中的消息长什么样？

在计算机网络中，我们学习过很多协议，比如 TCP、UDP、HTTP 等，其实协议就是定义如何解析数据，使得在网络上传递的二进制有意义。Kafka 作为一个消息队列中间件，与其生产者客户端、消费者客户端都通过网络进行通信，不可避免的需要设计自己的“协议”，以保证数据的传输和解析是有意义的。

而对于协议，从数据结构层理解，就是帧格式，Kafka 消息的帧格式如下，我们关注几个重要的字段：

  • Key：用于定位数据在哪个 partition，一个 topic 可能对应多个 partition 存储，需要通过 key 来指定消息在哪个 partition
  • Offset：标记该数据在 partition 的位置，这是 partition 有序性的必要设计
  • value：具体的数据，被压缩然后序列化

2. Kafka 如何存储消息？

在 Kafka 中，逻辑上是用 topic 对消息进行分类，但实际上一个 topic 由多个 partition 物理存储。

2.1 为什么要进行分区？

为了可扩展的吞吐能力，Kafka 在逻辑上用 topic 分类消息，物理上用 partition 存储消息，一个 topic 对应多个 partition。

这样做的优点就是给每一个 topic 的消息存储都带来了高度可扩展的吞吐能力：

  • 一个 topic 的不同 partition 可以在不同的 broker 上存储，提升并发读写能力
  • 单个 partition 消息有序存储，可以进行消息有序性扩展

2.2 partition 如何存储消息？

partition 可以理解为一个日志文件，每一行就是一条消息，写入时直接在文件后面追加，这样做的好处是既有高性能（顺序写）又能保证有序。

还有一个重要的概念 —— offset，可以理解为每个分区内，每条消息的位置编号，顺序递增，相当于消息在 partition 中的“下标”。

offset 是可靠性消费的重要数据结构，后面会介绍

（二）producer 生产者

对于 Kafka 来说，生产者本质上就是一个客户端，可以是任意一个服务、进程，其职责就是把消息写入 Kafka 集群。

具体来说，其具体的工作是：

  1. 准备要发送的数据，将数据封装成消息
  2. 对消息进行序列化，便于网络传输
  3. 设计分区策略，计算分区 key，将消息路由发送到指定的 partition

在可靠性方面，生产者可以通过配置 ACK 的策略来控制消息的确认级别，例如 acks = 0/1/all，分别对应不同的数据安全等级，同时配合重试、幂等性（enable.idempotence）等配置，可以实现“至少一次”的生产语义。

Kafka 将分区选择和消息路由下放到生产者侧，减少了 broker 端的计算和转发开销，整体提升了系统的吞吐能力。生产者还可以通过缓存、批量发送、异步 IO 等机制进一步提高写入性能。

可以看出，生产者端不仅是消息队列数据的入口，也是性能优化与可靠性控制的第一道关口

（三）consumer 消费者

对于 Kafka 来说，消费者本质上也是一个客户端，可以是任意一个服务、进程，负责从指定的 topic 拉取消息并进行处理。

1. 消费者的基本工作流程

具体来说，消费者的具体工作是：

  1. 向 broker 集群发送 pull 请求消息，请求某个 partition 上某个 offset 开始的消息
  2. broker 返回消息列表
  3. 消费者处理后，向 broker 集群提交自己消费的最后一个消息的 offset

2. 为什么要有消费者组？

在分布式系统中，消费者往往也是一个服务，往往一个消息由多个服务订阅消费，因此为了充分提高消费的吞吐量， Kafka 的消息消费是按照消费者组的方式消费的，也就是并发读！

  • Kafka 规定一个 partition，在一个消费者组内只能被一个消费者消费，也就是消费者组中两个实例不能消费同一个 partition，保证消息消费的有序性
  • 多个 partition 可以被多个消费者并行处理，进行横向扩展

3. 消费者组的管理

消费者一般通过消费者组进行管理，消费者组是 Kafka 实现并行消费和负载均衡的核心机制。多个消费者实例如果配置了同一个 groupId，就会组成一个逻辑消费组，共同消费并订阅同一个 topic。

Kafka 会在组内自动分配分区，每个分区在同一消费组内只能被一个消费者消费，以此保证消费的顺序性。

那么就自然带来两个问题：

  1. consumer 怎么知道自己要消费哪一个 partition？
  2. Kafka 如何进行分区分配？

3.1 group coordinator

group coordinator 是 broker 的一种身份，用于管理 consumer group 的。Kafka 通过一个特殊的内部 topic —— __consumer_offsets 来进行 coordinator 的确定。

__consumer_offsets 记录的是某个 consumer group 在某个 topic 的某个 partition 上的消费进度（offset），分为多个 partition，一个 partition 对应着一个 consumer group，它是多副本存储的，不同 partition 副本存储在不同 broker 上，而 leader partition 所在的 broker 就是这个 consumer group 的 coordinator。

一个 partition 其实我们可以理解为一个存储节点，多副本机制就可以理解为主从复制机制，会有一个 leader，多个 follower，通过读写分离提高吞吐性能

3.2 consumer 如何与 group coordinator 交互？

分区分配

  • consumer 启动后，向 broker 集群发送 MetadataRequest 获取整个集群的元数据（包括 broker 列表、_consumer_offsets 的 partition 分布等），然后根据自己的 groupId 计算自己所在的 consumer group 应该消费 __consumer_offsets 上哪个 partition，根据请求到的集群元数据找到该 partition 的 leader partition 所在的 broker，该 broker 就是该 consumer group 的 coordinator

  • consumer 发送 join group 请求给 group coordinator，group coordinator 将第一个 join 成功的 consumer 视为 leader consumer，等到所有成员加入成功或者 timeout 后无心的 join 请求后，将 consumer group 的元信息发送给 leader consumer 进行分区分配的计算

  • consumer group 根据分区分配策略计算分区分配，该策略通过参数（partition.assignment.strategy）配置，然后将分区分配结果发送给 coordinator，coordinator 广播给 group 内所有 consumer，至此完成分区分配，所有 consumer 知道自己消费哪个 partition

    分区分配策略在消费者端通过参数进行配置，主要配置如下：

    名字 分配规则 适用场景
    RangeAssignor 按分区号范围分配，比如 0-1 分给 c1、2-4 分给 c2 分区号有序场景、简单、需要自定义规则
    RoundRobinAssignor 轮询分配，比如 0 分给 c1、1 分给 c2… 尽量地均匀分配
    StickyAssignor 尽量保持原分配不变的情况下分配，分配剩余的分区 尽可能减少 rebalance
    CooperativeStickyAssignor Sticky 的改进版，支持渐进 rebalance Kafka 2.4+ 默认配置

再分区分配

当 group consumer 有成员变化的时候，会触发 rebalance，需要调整分区分配。下面介绍 rebalance 的过程：

  • 暂停消费：coordinator 通知所有 consumer 停止消费，提交已经消费的 offset、断开心跳，进入 rebalance 模式
  • 重新分区：
    • 所有 consumer 重新发送 join group request，第一个送到 coordinator 的 consumer 被认定为 leader consumer；
    • coordinator 将所有 consumer 的信息发给 leader consumer，由它根据策略进行重新分区分配；
    • leader consumer 将分区计算结果发给 coordinator，coordinator 广播给其他 consumer
  • 重新开始消费：consumer 得到自己的分区 partition 后，开始拉取消息进行消费

（四）broker 中转站

broker 可以理解为 Kafka 服务器节点，broker 就是存储 partition 的节点，并与生产者、消费者交互，对外提供读写服务。

对于 broker，我们需要理解他的三种角色：coordinator、leader、follower，这些角色都随着我们看问题的视角、以及 broker 本身存储的 partition 的角色有关。

1. leader

partition 是多副本部署在 broker 上的，对于一个 partition 集群，只有一个 broker 存储 leader partition、其他 broker 都存储的是 follower partition，从单个 partition 的视角来看，这里出现了 broker 的第一种角色 —— leader。

一个 broker 可能既是 leader、又是 follower，因为 broker 中存储着多个不同的 partition，这些 partition 可能是 leader、也可能是 follower。

2. coordinator

broker 的另一种角色是 coordinator，管理消费者组。每个消费者组都会对应订阅 __consumer_offset 这个 topic 的一个 partition，维护 broker 和 consumer 的消费进度。

coordinator 存储的是这个消费者组消费的 leader partition，负责与各个 consumer 维持心跳、维护 consumer 的元信息、与 leader consumer 配合进行 rebalance。
