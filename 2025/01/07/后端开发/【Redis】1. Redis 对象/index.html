一、Redis 对象简介

Redis 是 K-V 数据库，其数据类型丰富，最主要的有 5 种：

类型 核心语义 典型应用场景 和其他类型的本质区别
String 单 key 对应 一个值 缓存对象(josn)、计数器、分布式锁、简单 KV 唯一的单值语义，支持原子数值操作（INCR）
Hash key → field-value 映射 用户信息、商品属性、对象缓存 对象级访问，避免整体序列化，字段可单独修改
List 有序、可重复元素集合 消息队列、任务队列、时间线 支持两端操作（栈 / 队列），强调顺序
Set 无序、去重元素集合 标签系统、关注关系、去重统计 天然去重，支持交并差运算
ZSet 有序 + 去重集合 排行榜、积分系统、延迟队列 在 Set 基础上增加 score，实现排序和范围查询

Redis 为了极致的时间和空间性能，每种数据都有多种编码方式以应对不同的场景，但对使用者是透明的。下面从数据结构开始，剖析 Redis 的数据结构设计，再介绍各种对象底层用什么数据结构，最后介绍各种对象的 API，深入浅出。

二、Redis 对象数据的组织与底层数据结构设计

（零）总揽全局

Redis 作为一种高性能的轻量级中间件，要解决数据怎么高效存储的问题。

无论是系统设计、还是存储结构的设计，都离不开具体的场景，那么 Redis 要存储的场景有哪些呢？

  • 单值场景：存储数字、字符串，于是有了 SDS 的设计
  • 存储一组数据的场景：有了 ZipList，ListPack，QuickList
  • 存储映射关系的场景：有了 Dict
  • 存储有序的一组数据的场景：有了 SkipList

（一）Redis Object

在 Redis 中，所有对象都被封装成 Redis Object。

核心字段：

  • type：类型，其值是宏定义，区分对象的类型
  • Encoding：编码方式，同一种对象不同场景下有不同的编码方式，对应不同的存储结构
  • Lru：记录对象的访问信息，用于内存淘汰策略
  • refcount：引用计数，描述指向该对象的指针个数
  • Ptr：数据指针

（二）Redis 基本数据类型的存储结构

基本数据类型，比如 Java 中的基本数据类型为 int, long, double, String 等，代表了一个数据到了这个语言后以什么作为最基本的存在方式。

在 Redis 底层中，基本数据类型有三种：

  • int
  • long
  • SDS，存储字符串

其实也可以说是两类：整型类和字符串

而 Redis 对外暴露出的对象，比如 String，List 等，本质就是这些数据类型以一定的方式进行组合存储，实现具体的语义。

Int, long 就没什么好说的了，二进制表示就可以存储。字符串的每一个字符也是二进制编码罢了。但是对于每一个字符怎么组织，Redis 并没有采用 C++ 的 String 的存储方式，而是进行了优化，以 SDS 来存储。下面重点介绍 SDS！

1. Simple Dynamic String

1.1 为什么需要 SDS

SDS 的出现是对传统 C++ 的 String 的优化。传统 String 存在的问题：

  • 非二进制安全，以\0标志结尾
  • 获取字符串长度时间复杂度为 O(n)
  • 每次对字符串进行追加都需要重新分配内存

1.2 SDS 如何解决传统 String 痛点

SDS 是如何解决这些问题的？通过其数据结构也很好看出来：

  • Len ：记录字符串存储了多少字节字符（1 字符 = 1 字节），O(1) 时间可以得到字符串长度
  • Alloca：字符串申请了多少字节内存空间，一般大于 len，可以通过预留空间的方式减少扩容次数，并且可以提前扩容
  • 不存在二进制安全问题，判断 len == alloca 即可知道是否到结尾

1.3 SDS 扩容机制

SDS 通过空间预留机制减少扩容次数。

下面介绍其空间预留规则：free = min(len, 1MB)

  • len < 1MB，alloc = 2 * len，预留 len 字节的空间
  • len >= 1MB，alloc = 1M + len，预留 1MB 的空间

1. Dict：K-V 的核心组织结构

Dict 是 Redis 中最核心、应用最广泛的数据结构，因为 Redis 本身就是 K-V 型数据库，而其 K-V 存储就是靠 Dict 组织的！

1.1 数据结构

Redis 的 Dict 数据结构主要需要掌握三层，最外层的是 Dict，为了支撑渐进式扩容机制，Dict 封装了 dictht，而 dictht 内部核心结构是 dictEntry，下面我们层层解析。

Dict 的数据结构如下，主要是为了封装 dictht，支持渐进式扩容：

下面看 dictht 的数据结构，其核心核心字段 table，本质上是一个指向 dictEntry 数组的双指针，table 就是真正的哈希表！dictEntry 是哈希表的元素。

1.1.3 dictEntry

关键字段：

  • key：任意类型

  • v：整型、浮点或任意类型，但都是 64 位的

  • next：指向下一个 dictEntry，即发生哈希冲突的时候采用拉链法解决

1.2 为什么要 dictht 有 sizemask 字段？

在哈希中，我们第一件要做的事情就是将元素对应的下标 index 计算出来，为了使得哈希分布尽量均匀，常见的做法是 hash % size，也就是哈希值对槽位数量取模。

但是取模运算没有位运算快，因此在 size 是 2 的幂次方的前提下，有如下公式成立：

hash % size=hash & (size−1)hash\ \% \ size = hash \ \& \ (size - 1) hash % size=hash & (size−1)

恰巧，容量为 2 的幂次方也很方便分配内存和扩容，因此哈希表容量大小一般都是 2 的幂次方。

因此 Redis 缓存了 size - 1 并封装到哈希表的结构中。

1.3 扩/缩容机制

为了实现对内存的极致利用，Dict 有扩容/缩容机制。下面从扩容/缩容条件、扩容具体过程来介绍。

1.3.1 扩容/缩容时机

首先要了解负载因子的概念，Redis 中将负载因子 loadfactor 定义如下：

loadfactor=ht[0].usedht[0].sizeloadfactor = \frac{ht[0].used}{ht[0].size} loadfactor=ht[0].sizeht[0].used​

扩容时机

  • Loadfactor >= 1：此时哈希槽已经满了，再加入元素一定会发生哈希冲突，如果此时 Redis 后台没有持久化相关任务（AOF rewrite / RDB）时，会触发扩容

  • Loadfactor >= 5：此时哈希碰撞已经很严重了，并且链表也比较长了，无论后台是否有 bgsave 等在运行，都会立即扩容

缩容时机

  • Loadfactor < 0.1 时触发缩容机制，如果此时后台有持久化任务则暂时不缩容
1.3.2 扩/缩容大小的设计

无论是扩容还是缩容，变化的容量大小都是：第一个大于 2*used 的 2 次幂

1.3.3 为什么扩容/缩容要考虑后台持久化任务？

Redis 的持久化相关任务有哪些？

  • RDB 持久化：bgsave

  • AOF 重写：bgrewriteaof

Redis 的持久化任务共同点是会 fork 子进程，采用 COW ( copy-on-write ) 机制，一旦父进程修改大量修改内存（扩容/缩容），页面就会复制，那么内存占用就会骤增！

扩容/缩容正是创建新的哈希表、大量写内存的修改内存操作。

因此，rehash + fork 会有内存暴涨的风险！Redis 在有持久化任务时尽量不进行扩容/缩容操作。

1.3.4 扩容过程 —— 渐进式扩容

如果没有触发扩容，rehashidx 默认为 1，表示没有触发扩容，此时 Dict 只用 ht[0]，ht[1] 指向空指针。

如果触发扩容，分为三步走：

  1. 为新的哈希表申请新的扩容后的内存空间，ht[1] 指向这片内存的首地址
  2. rehash 设置为 0，表示扩容的开始
  3. 迁移 ht[0] 的槽到 ht[1]，主要有 2 方面的动作
    1. 每次对 dict 作增删改查操作，都会顺带将 ht[0] 的一个槽迁移到 ht[1] 上，同时 used–，rehash++
    2. 后台周期任务也会在空闲时执行迁移操作
  4. 当 used 为 0 时表示迁移完成，此时将 ht[0] 指向空指针，然后交换 ht[1] 和 ht[0] 的指针，rehash 置为 -1 表示扩容结束

2. 紧凑型列表数据结构：ZipList/ListPack

ZipList 是为读多写少的小列表场景设计的数据结构，但存在级连更新问题，ListPack 是在 ZipList 基础上的优化，Redis 7.0 以后已经彻底抛弃 ZipList，但 ZipList 的结构是 Redis 紧凑型列表数据结构的基石。

2.1 ZipList/ListPack 数据结构

本质上，ZipList 就是一个字节数组，在 Redis 内部就是一个 unsigned char 字节数组，不同位置的字节按照约定格式解析成头部字段或 entry 字段。

char 类型占 1 字节

这是一个指向内存的指针，需要我们逐个字节地解析；主要分为头部字段和 entry。

  • 头部字段：
    • Zlbytes：ZIPList 占了多少字节数据
    • Zltail：ZIPList 末尾节点相对于 ZIPList 起始指针偏移的字节数，用于迅速定位尾部节点
    • Zllen：entry 的个数
  • entry：表示压缩列表中的数据节点，长度不固定。其中 Zlend 是特殊的 entry，大小固定为 8 位，值为 0xFF

entry 数据结构

entry 是压缩列表中的数据节点，虽然也是一串字节数据，但也有其特定的解析规则。其数据结构组织形式如下：

  • Prevlen: 上一个节点的长度（字节），通过这个字段可以定位到上一个节点的起始地址，用于反向遍历
  • encoding：编码类型，包含当前节点的数据类型信息和该节点的数据长度信息，可以用于正向遍历
  • content：实际数据

2.2 ZipList 的增删改查

基于 ZIPList 的增删改查操作是怎么样的呢？效率如何？

2.2.1 查询操作
  • 查询数据总量，O(1)，zlen 已经记录了这个数据；但是 zlen 只有 2 字节长度，当 entry 数量超过 2162^{16}216 时 zlen 失效，查询数据总量的时间复杂度降级为 O(N)
  • 查询某个数据，O(N)
2.2.2 更新操作
  • ZipList 提供了头尾插入、删除节点的能力
  • 操作的平均复杂度为 O(N)，每次更新都需要移动 entry

2.3 连锁更新问题

2.3.1 为什么有连锁更新问题

ZipList 的连锁更新问题主要有 2 个重要的本质原因：

  1. encoding 编码是变长的，不同数据类型有不同的编码长度
  2. prevlen 是变长的，不同类型长度的数据有不同的长度的 prevlen 表示
  3. 现有的 entry 节点的设计使得每一个节点与前一个节点的长度耦合

这就导致一个问题，如果一个 entry 数据发生了变化，比如长度变长了，可能导致其后面节点的 prevlen 变长，后面节点变长又可能导致更后面的节点变长，使得**节点的长度会连锁影响到其后续的节点变化。**这就是连锁更新问题。

连锁更新有什么影响？

  • 性能不稳定，连锁更新的平均时间复杂度是 O(n2n^2n2)，触发连锁更新可能带来性能不稳定
2.3.2 prevlen 和 encoding 的设计如何引起连锁更新？

数据长度不同，prevlen 长度也不同

28=2562^8=25628=256

  • 如果前一个节点数据长度小于 254，prevlen 占 1 字节
  • 如果前一个节点数据长度等于 255，则改节点当成 zlend 处理
  • 如果前一个节点数据大于 255，则 prevlen 用 5 字节存储

数据类型不同，encoding 长度也不同

2.4 ListPack 优化

2.4.1 数据结构的重构

ListPack 是为了解决 ZipList 连锁更新问题而诞生的。连锁更新问题的本质其实在于每一个节点与上一个节点的长度耦合。

ListPack 重构了 entry 的结构，让每个 entry 存储自己的长度信息，彻底解决了连锁更新问题。其数据结构如下：

  • Encoding-type：编码类型
  • Element-type：元素类型
  • Element-tot-len：存储整个节点除了以外的长度
2.4.2 基于 element-tot-len 的反向遍历
  • Element-tot-len 的每一个字节的第一个元素表示是否结束（0 表示结束、1 表示继续），剩下 7 位存储数据大小
  • 当我们需要找当前元素的上一个元素，只需要往前移动指针，直到找到上一个 entry 的 element-tot-len 的结束字节，再算出上一个节点的位置即可

3. 通用型列表数据结构：LinkedList

LinkedList 是 Redis 中典型的双向列表，是通用的列表数据存储方案。当列表的 entry 过多、entry 过大时，早期的 Redis 会将紧凑型数据结构转为 LinkedList 存储。

3.1 LinkedList 数据结构

下面是 LinkedList 的数据结构，其实就是很经典的双向链表设计，额外封装了一个长度信息 len。

3.2 LinkedList 的特点

优点

  • O(1) 的头尾插入、删除性能，不需要移动元素
  • 结构简单，行为稳定，非常适合频繁插入/删除的场景

缺点

  • 内存开销大，每个节点会有至少 2 个指针（16 字节）的额外开销
  • 内存碎片严重，离散的内存分配
  • CPU cache 不友好，缓存命中率低

在绝大多数的系统、中间件，这些可能都不是很严重的问题。但 Redis 是追求极致性能的轻量级中间件，这些都是致命缺点，会大大削弱 Redis 的性能，与 Redis 极致内存 + cache 友好的设计目标背道而驰。

因此后续的 Redis 很快有新的数据结构优化 LinkedList，目前 LinkedList 主要用于 Redis 内部后台任务的调度等系统运维工作中。

4. QuickList: 列表的工程化组织

列表类型的数据，对于小列表可以采用紧凑型数据组织方式，但大列表采用 LinkedList 会有内存碎片、内存占用大、CPU cache 低的缺点。如何解决这个问题呢？—— 折中。

QuickList 的设计就是紧凑型数据类型和双向链表数据类型的结合，既保证了空间的局部性，又保证了插入效率。

4.1 QuickList 的设计思想

QuickList 的设计思想很简单 —— 分治、折中。

既然对于大列表无法发挥小列表的空间局部性优势，那么就把大列表用链表的方式组织成一个个小列表，每一个小列表用紧凑型数据结构存储。

这样既保证了空间的局部性、又保证了插入效率，简单、有效、巧妙的设计思路。

5. SkipList: 有序列表数据的组织结构

为了支撑有序列表的数据高效、简单存储，Redis 设计了 SkipList 数据结构。

5.1 SkipList 解决什么问题？

有序数据的动态维护可以理解为：在数据不断插入/删除的情况下，始终保持数据有序、并支持高效的查找。

这类问题叫做“动态有序集合（Dynamic Ordered Set）”

数据的动态有序存储是我们非常常见的需求，假设没有 SkipList，我们如何实现？现有的数据结构有：

  • Dict
  • ListPack/ZipList/QuickList

显然 Dict 并不合适，因为它主要是做数据的映射的，存储键值对；对于列表类型的数据结构，如果需要动态排序，则会有很频繁的元素移动，并且排序的复杂度很高。

那么我们应该设计一个新的数据结构来实现我们的需求 —— 有序数据的动态维护。

动态维护有序数据的传统方案

如果数据能够按照二叉搜索树来存储，那么元素的插入、查找效率都将降低为 log(n)；

但是如果树不平衡，可能会退化成链表，导致效率降低。

因此对于动态有序集合的传统解决方案是 —— 平衡二叉搜索树（BST），主要分为两种：

  • 红黑树：一种弱平衡的 BST，通过颜色规则约束树高；增删改查效率都为 O(logn)
  • AVL 树：一直强平衡的 BST，对树高严格约束，查找效率严格 O(logn)，插入效率可能较低（可能涉及到频繁的旋转操作）

Redis 的考量

由于红黑树、AVL 树的实现复杂度高，并且树形结构天然 cache 不友好，因此并没有采用传统的解决方案。

而是巧妙地设计 SkipList 数据结构，以概率保证平均性能，同时大大降低了实现复杂度，且保留了空间局部性优势。

5.2 SkipList 的设计思想

首先得清楚地认识到，SkipList 并不是 Redis 开发者设计出来的，而是在比 Redis 了 20 多年的论文中提出来的。

该论文的核心观点是用概率平衡的多层链表，代替复杂的平衡树

SkipList 的设计思想一句话可以概括：用概率平衡的多层链表，代替复杂的平衡二叉树。

而在 Redis 中，以工程化的方式实现了 SkipList，使其不仅支持动态维护有序数据，还支持双向遍历、member/score 的组合键排序等。

5.3 SkipList 数据结构

  • header 是头节点，tail 是尾节点
  • length 是节点数量
  • Level 是当前最大层数

SkipList 节点结构：

  • Ele: 存储节点真正的数据
  • score：SkipList 排序的依据

5.4.1 基于 SkipList 的查询

假设查询分数为 45 的数据，从第一个元素开始。

  1. 优先跳最大步长，选择二级索引（level[1].span > level[0].span），找到值为 35 的节点
  2. 若当前找到的节点值小于要找的值，继续第一步，找到值为 55 的节点
  3. 若当前找到的节点值大于要找的值，则回退上一个节点选择步长较短的索引跳跃，找到值为 45 的节点
  4. 若当前找到的节点值等于要找的值，结束
5.4.2. 基于 SkipList 的插入

插入其实也是基于查询的，对于链表类型的数据插入的时间复杂度是 O(1)，也就是移动几个指针的事情。但跳表需要多一步，就是新插入的节点需要随机确定其层高。

比如插入一个 score 为 36 的数据，具体过程如下：

  1. 查询到第一个值大于 36 的节点，即 45
  2. 然后生成一个新节点，通过随机的方式判定其层高（假设为 3），其 score 为 36，然后将该节点插入

5.5 SkipList 单个节点的层高如何确定？

为了使得以平衡的概率模拟平衡二叉树，需要每个节点的层高比较随机地取，这样才能在各种场景展现比较平均的性能。

Redis 以概率均衡的思路来确定插入的心节点的层数：

数学原理 —— 几何分布，独立重复事件

  • 节点能否增加一层的概率设置为 p，一般设置为 0.25
  • 初始化 level = 1
  • 生成一个 [0, 1) 的随机数，模拟一次独立随机事件（是否能成功增加一层），如果随机数小于等于 p 则表示事件成功发生，那么 level++，继续生成随机数
  • 重复上一步直到 level 达到最大层数或者事件发生失败（即随机数大于等于 p）

5.6 SkipList 性能

可以类比平衡二叉树的性能。

  • 平均时间复杂度为 O(logN)
  • 最坏时间复杂度为 O(N)
  • 在实际生产环境中，体现的基本是平均时间复杂度

6. 紧凑型整数集合：INTSET

这是 Redis 针对小整数集合专门设计的数据结构。

6.1 数据结构

其数据结构设计比较简单：

  • encoding：决定每个整数多大（字节）
  • Length：元素个数
  • contents[]：整数数组

6.2 数据的维护

INTSET 主要是为整数集合设计的，元素是唯一的。

  • 查询操作 O(logN)：用二分查找定位要查询的元素

  • 插入操作 O(N)：二分查找定位到要插入的位置，分三种情况

    • 值已经存在，则不插入
    • 如果要插入更大 encoding 的元素，则所有元素 encoding 升级，重新分配内存，旧元素拷贝到新数组、插入新值
    • 值不存在，则插入新元素，此后的元素全部往后移动一位

  • 删除操作 O(N)：二分查找定位元素，删除后移动数组，不会降级 encoding

    插入更大的整数，可能会带来 encoding 的升级，要重新内存分配并进行元素迁移，这是一个比较重的操作。

    对应的，删除大整数却不会带来 encoding 的降级，这是为了避免频繁触发内存重新分配带来性能不稳定。

6.3 INSET 的特点

  • 内存极其紧凑，cache 友好
  • 元素有序存储，支持二分查找

三、Redis 五种核心对象

掌握了 Redis 对象数据的组织以及底层数据结构的设计后，再来看 Redis 对象，实际上就是各种数据结构根据不同场景的嵌套、组合。

Redis 对外主要提供了 5 种对象类型：

  • String

  • List

  • Hash

  • Set

  • ZSet

无论是哪种对象，都是由 RedisObj 封装的。

（一）String

1. 简介

String 是 Redis 对外提供的字符串对象，一个字符串最大为 512 MB，可以通过配置项proto-max-bulk进行修改。

Redis 的字符串对象的应用场景主要有：

  • 存储字节数据、文本数据、序列化后的对象数据等
  • 在缓存场景中，Redis 最常见的就是存储 json 数据
  • Redis 由于其单线程处理天然原子性，String 类型可以存储整型数据并且对外提供 INCR 自增之类的 API，使得其 String 类型也天然适合计数场景，比如计算访问次数、点赞、转发、库存等

2. API 使用

值得关注的是 set 和 setnx 的使用，在实现分布式锁的时候比较重要，还有 px 和 ex 参数，用于设置过期时间。

3. 数据结构

我们以 redisObj 来看待任意一个对象，因为 redisObject 就是对对象的封装。这里再次回顾 redisObject 的数据结构：

  • 不同对象只是 ptr 指向的地址不同
  • encoding 控制编码方式
  • 不同数据类型的对象 type 不同，这个是宏定义的枚举

3.1 三种编码方式

其实我们也很容易把握规律：

  • 当对象内存占用较小时就采用内存紧凑的数据结构：EMBSTR, LISTPACK, ZIPLIST, INT 等
  • 当对象内存占用较大或元素数量多的时候，就采用通用型数据结构：QUICKLIST, SDS, DICT 等
  • 当需要兼顾有序性和性能时，采用 SKIPLIST

String 有三种编码方式，本质上是针对不同场景进行的优化：

  • INT 编码方式：整型数据，并且大小在 long 范围内，直接用 long 进行表示（二进制）

  • EMBSTR 编码方式：小字符串，此时 String 用 SDS存储，但 SDS 和 redisObject 是连续的内存空间，一次性内存分配

    所以是 embedding 编码，意思是 String 嵌入到 redisObject 的内存空间

  • RAW 编码方式：大字符串，此时 String 用 SDS 存储，ptr 指向 SDS 的首地址

3.2 不同编码方式的转换时机

  • 当 String 存储的数据不是整数类型，或者整数大小超过 long 的范围，从 INT 变成 EMBSTR
  • 任务写操作之后，EMBSTR 都会转化成 RAW
    • EMBSTR 的内存是一次性分配的，任何修改操作都可能导致大小变化需要重新分配内存带来较大的性能损耗
    • 因此 EMBSTR 的适用场景是只读的紧凑型 String

（二）List

1. 简介

List 是有序、可重复的 String 对象的集合。List 中的每个元素，本质上是一个 String 对象。

2. 应用场景

下面只介绍 2 种应用场景，实际上还有非常多，这里先作一个抽象，下面其实是具体业务的方案。

List 本质上就是一个队列，核心特点是一组数据，有序存储。可以用在什么地方主要可以把它看成两种东西：

  1. 消息队列：当这个场景满足消息队列的场景，但对可靠性要求不高时可以考虑
  2. 有序数据容器：当需要一个高性能的有序数据容器时，可以考虑

2.1 轻量级 MQ

如果在一些需要异步处理的消息/任务中，这个异步消息/任务处理失败了也没有关系，那么就可以用 List 来充当 MQ。具体业务场景：

  • 用户下单后异步发送短信
  • 用户注册后异步发送欢迎通知
  • …

为什么 List 可以充当轻量级 MQ

  • MQ，也就是消息队列，可以理解为传递消息的管道，是经典的生产者-消费者模型，理论上任何队列都能作为消息队列，都有消息队列的语义。显然 List 满足 MQ 的基本语义
  • List 相比于一般的队列有其独特的优势，它是 Redis 的对象，并发性能高，写入快，支持阻塞消费；这使得它很适合作为一个轻量级的 MQ

2.2 最近记录/时间序列

核心场景：只关注最近 N 条数据

常见场景：

  • 存储用户最近浏览的商品
  • 存储用户最近搜索的关键词
  • 存储用户最近登陆的设备列表

为什么用 List？

  • List 是天然有序的，新数据从一端写入
  • 可以使用 LTRIM 控制长度，截取最近存储的数据

3. API 使用

特点是以 L 开头，并且数字的正负常带有正向、反向的语义。

4. 数据结构

在紧凑型的应用场景，有 2 种数据结构可以用：

  • ZipList
  • ListPack

当然 ListPack 是对 ZipList 的优化，因此一般是第二种。

当在元素较多或某些元素特别大的场景下，也有 2 种数据结构可以用：

  • LinkedList，通用的双向链表
  • QuickList

QuickList 既保证了空间局部性又保证了插入性能，一般用这种。LinkedList 在早期的 Redis 中有所应用。

早期的 Redis List 编码有两种，分别为：ZipList 和 LinkedList

现在主流的 Redis List 编码也是两种，分别为：ListPack 和 QuickList

（三）Hash

1. 简介

Hash 是存储 String 到 String 的映射的集合。

2. 应用场景

Hash 主要用于缓存结构话对象，比如用户、商品、订单等，可以按字段原子更新数据，避免整体序列化带来的性能和并发问题。

特别适合缓存一个对象的多个属性，当对象字段会被频繁、独立地更新时，Hash 能避免整体序列化和并发覆盖问题状态。

举例说明 Hash 的实际应用场景 —— 用户信息缓存

假设用户表：

访问特点：

  • 查询非常频繁
  • 经常只修改其中某个字段：头像、用户名、升级
  • 不希望每次都打到数据库

方案一：用 String 存储 json

这是很多系统一开始的方案，存储对象的 json 序列化数据。

当用户修改头像时：

  • 先 get 获取用户 json 数据
  • 再 json 反序列化成对象，修改 avatar 字段
  • 再序列化 json，set 插入到 redis 的 user:1 中

存在的问题：

  1. 性能低，频繁序列化和反序列化，频繁更新缓存
  2. 并发更新问题，如果用户并发更新两个字段，比如在 avatar 的修改写回缓存前又更新了 name 字段，那此时读到的 avatar 还是旧的，修改完 name 再 set 回去后会覆盖原来对 avatar 的更新！

方案二：用 Hash 存储 user 对象

优势：

  • 直接用 Hash 命令原子修改某个字段的信息，比如 hset user:1 avatar b.png，不存在并发问题，也不存在序列化和反序列化的性能问题

3. API 使用

操作基本是 h 开头。

3.1 hscan

比较特殊的哈希操作，类似于分页查询。百万级数据的大哈希表时必须使用，避免 hgetall 一次性获取所有键值对导致 Redis 阻塞。

语法：hscan key cursor [match <pattern>] [count <cnt>]

  • cursor 游标，可以理解为第几页，从 0 开始
  • match 和 count 都是可选的
    • match 过滤筛选对应的 key 的键值对，用正则表达式表示 pattern
    • count 表示最多扫描多少个哈希桶，表示着扫描的强度

3.2 hset & hsetnx

主要想介绍的是 hsetnx：

当 name 不存在对应 value 的时候才会插入成功。

4. 数据结构

  • 紧凑型：采用 ZipList/ListPack 编码

  • 通用型：采用 HashTable 编码，底层就是 Dict 数据结构

合适从紧凑型转换成哈希表编码？

满足下面两个条件之一就会触发编码转换：

  • 键值对数量超过阈值
  • 任意一个键值对长度超过阈值

（四）Set

1. 简介

Set 是无序、不可重复的 String 集合。

常见的应用场景是需要无序集合（去重）的业务，比如某个用户关注了哪些公众号等业务。

2. API 使用

2.1 基本 API

特点是以 s 开头。

为什么 scard 代表查询元素个数？

cardinality 是基数的意思，在数学中代表集合的元素个数。这个 card 就是 cardinality 的缩写。

2.2 大集合必须用到的查询 API —— sscan

对于大集合，如果直接 smembers 可能会阻塞住整个 redis，影响性能，而实际使用中也极少地要得到所有数据。

因此对于大集合，有 sscan 命令，用于分批、按特定规则读取特定模式的子集。可以理解为 set 的分页查询。

**sscan 语法：**sscan key cusor [match ] [count ]

  • 方括号内为可选的配置，分别表示==过滤==什么模式的元素以及最多读取多少个桶去找这样的元素
    • match 后面的 pattern 是正则表达式，过滤特定的 string
    • count 后面的 cnt 是数字，表示最多==去读多少个桶查询这样的元素==
  • cursor 是游标，第一页从 0 开始，默认一页读 10 个桶
  • key 是键，也就是定位到对应的集合

3. 数据结构

  • 紧凑数据类型：当 Set 中仅有 long 可以表示的整数时，采用 INTSET 编码存储

  • 通用数据类型：采用 Dict 数据类型存储，dictEntry 的 key 存储集合元素，dictEntry 的 val 置为 null

（五）ZSet

1. 简介

ZSet 存储带权重的有序集合，每个元素唯一，可以按照 score 进行排序。

核心语义：

  • 元素唯一
  • 每个元素与一个 score 绑定
  • 集合始终按照 score 排序

2. 应用场景

ZSet 非常适合需要动态排序的场景，比如 TOP K、排行榜、热榜、定时任务调度等。

ZSet 还非常适合需要范围查询的场景，因为 ZSet 原生支持范围查询。

3. API 使用

这里重点需要关注 zadd 的用法，有几个扩展参数.扩展参数都放在 key 后，数据元素前。

  • 语法：zadd key score member [score member …]
  • 参数：
    • nx：仅添加新成员
    • xx：仅更新存在的成员，不添加新成员
    • lt：仅更新新的分值比当前分值小的成员，不存在则新增
    • gt：仅更新分值比当前分值大的成员，不存在则新增

4. 数据结构（重点）

ZSet 首先具备 Set 的性质，因此和 Set 的存储结构有些许类似。

ZSet 也有两种编码方式：

  • 紧凑型：ZipList/ListPack

  • 通用型：SkipList + HashTable

    • HashTable 可以快速定位 member，非常适合已知 member 查 score 的场景，因此 zscore 是 O(1) 的操作
    • SkipList 可以维护元素的顺序，非常适合已知 score 查 member 的场景，以及非常适合范围查询
